# ADR 0002 — Authentication and tenant authorization

Status: approach approved by EAAP-003; implementation pending independent review. EAAP-000 through EAAP-002 are accepted. This records the assigned authentication design and bounded implementation choices; it approves no later identity-platform features.

## Identity, authorization, and ownership

Authentication establishes an immutable user UUID. Authorization verifies current enabled state and the requested tenant membership in trusted server code. Tenant selection is explicit in `GET /api/v1/tenants/{tenantId}/context`; the URL, headers, roles, and JWT tenant claims are never membership proof. All three approved roles may use this verification operation: OWNER reserves future ownership operations, ADMIN future administration, MEMBER standard membership. No other permissions or administration APIs exist.

The `identity` module follows API → application → domain. Domain records enforce email normalization and typed membership roles without Spring/JPA/HTTP dependencies. Application use cases coordinate credential verification and membership authorization through specific persistence/password/token/tenant-read ports. Infrastructure provides JDBC, Spring Argon2, Spring JWT facilities, and explicit transaction management. Thin controllers perform bounded transport validation. JDBC is used deliberately for narrow SQL functions and exact connection ownership; no speculative JPA entity/repository framework is added.

## Passwords and login

`POST /api/v1/auth/login` accepts only JSON with email and password. Email is stripped and lowercased using `Locale.ROOT`, limited to 254 input characters and the documented ASCII mailbox/domain syntax in `Email`. Internationalized identifiers and quoted mailbox syntax are not supported in this initial version. Password input is nonblank, at most 128 characters. The entire body is limited to 4096 bytes before parsing, including chunked input. Unknown JSON properties, duplicates, trailing JSON, missing fields, and query parameters fail with 400. Other media types fail with 415. Tokens are returned only in a no-store response with `accessToken`, `tokenType=Bearer`, and `expiresIn=900`.

Spring Security `Argon2PasswordEncoder` uses Argon2id v19, 19 MiB memory, two iterations, parallelism one, a random 16-byte salt, and 32-byte output. Bouncy Castle `bcprov-jdk18on:1.87` is the supported encoder's required implementation dependency, explicitly pinned because Boot does not manage it. No custom cryptography is implemented. These parameters meet the [OWASP minimum](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html); see [Spring's encoder documentation](https://docs.spring.io/spring-security/reference/6.5/features/authentication/password-storage.html). Hash strings encode algorithm, version, salt and costs. Future reviewed parameter upgrades should use `upgradeEncoding` after successful verification and an explicitly privileged password-update mechanism; runtime has no password-write grant today. Existing hashes are not silently overwritten.

Wrong, unknown and disabled credentials produce the identical 401 `invalid_credentials` response. Unknown users perform verification against a randomly generated dummy hash; disabled users still perform verification. This limits obvious enumeration differences without claiming constant end-to-end timing. No password or hash is returned or deliberately logged. DTO string representations redact credentials and tokens.

Local abuse protection allows five attempts per direct peer IP and twenty total attempts per process per fixed minute, including invalid input attempts that reach the controller. Forwarded headers are ignored. The address map is capped at 1024 entries (the global attempt cap normally bounds it further), expired windows clear it, and at most two password-verification operations run concurrently without queueing. Excess returns 429 with Retry-After 60. Fixed-window boundaries, process restarts, shared NAT and multiple replicas limit this protection. **This is local development protection, not distributed production abuse prevention.** Production rollout requires a separately approved coordinated limiter/ingress policy, TLS termination and monitoring; no Redis or new service is selected.

## JWT and signing configuration

Spring Security Nimbus encoder/decoder issue and validate RS256 only, using a dedicated matching RSA key pair of at least 2048 bits. Required runtime settings are `AUTH_PRIVATE_KEY` (PKCS#8 PEM resource), `AUTH_PUBLIC_KEY` (X.509 PEM resource), `AUTH_ISSUER`, `AUTH_AUDIENCE`, and `AUTH_KEY_ID`. The decoder explicitly restricts algorithm, verifies signature, issuer, audience, expiration with zero clock skew, canonical UUID subject, nonfuture issuance, positive lifetime no longer than 900 seconds, nonblank jti, and the configured kid. Unknown keys, missing/wrong claims, malformed or unsigned tokens fail closed. Only `sub`, `iss`, `aud`, `iat`, `exp`, `jti` are issued. No tenant grants, profile data, or credentials are embedded. See [Spring JWT support](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html).

If both key paths are absent, health remains available but issuance returns 503 and every bearer token is rejected. There is no generated fallback key. Partial, unreadable, mismatched or weak key configuration fails startup with a sanitized message. Offline migration/bootstrap modes instantiate no JWT infrastructure. Private keys belong in protected runtime files outside the repository/build context, never frontend/Python clients or images. Optional `compose.auth.yaml` mounts an external dedicated key directory read-only in the existing control-plane service. Operators must manage file access, secure backup, rotation, and time synchronization. One configured key is accepted at a time; replacement invalidates old tokens immediately. Overlapping rotation/JWKS distribution is not implemented.

Spring's resource server validates tokens before conversion. The conversion checks current user enabled state and creates no authorities from caller claims. Unknown/disabled users get 401, including with a correctly signed unexpired token. Sessions and request caching are disabled, no cookie credentials/form login/basic auth or wildcard CORS is configured. CSRF remains enabled except POST login: this endpoint accepts JSON, rejects query credentials, and creates no cookie/session authentication. The only bearer tenant operation is a read-only GET with explicit Authorization header. Future state-changing endpoints must review CSRF and CORS independently. Unspecified endpoints remain denied.

## Schema and database privileges

V1 is unchanged. V2 creates global `platform.users` with UUID primary key, unique normalized bounded email, nonnull Argon2id hash, enabled flag and timestamp constraints. `platform.tenant_memberships` has a `(user_id, tenant_id)` primary key, foreign keys, constrained OWNER/ADMIN/MEMBER role and creation timestamp. The email unique index supports login; the composite key supports exact membership lookup. A tenant-first index supports the tenant foreign key. There is no redundant user-only index or membership cache.

Global identity records are not tenant business rows. Runtime receives **no direct SELECT or write grants** on either identity table. Three migration-owned SECURITY DEFINER functions with empty search_path and no PUBLIC execution expose exactly email→credentials, UUID→enabled, and (user UUID, tenant UUID)→current enabled membership role. They use static parameterized predicates, never dynamic SQL, and cannot discover tenants. Owning migration credentials remain privileged and never enter the HTTP process. Password hashes are available only through the login function to trusted runtime code; compromise of runtime SQL access can still query identities by known emails and is outside this boundary's guarantees.

New `eaap_identity_operator` is an offline login with CONNECT/schema USAGE, insert-only identity creation and narrow SELECT (users excludes hashes), no UPDATE/DELETE/DDL/ownership/role membership/superuser/BYPASSRLS. Registry INSERT and SELECT policies apply only to this operator and require its transaction-local tenant UUID. Existing runtime registry policy and forced RLS remain unchanged; migration ownership is not relaxed. Administrator provisioning adds the role and distinct credential before V2, including existing volumes. Operator error verbosity is terse, statement logging is disabled and bound-parameter logging is suppressed to prevent hashes in failed-row/SQL logs. Application diagnostics log correlation ID and event type, never SQL/provider exception contents. PostgreSQL privileged operators must preserve these logging controls and protect database logs.

## Trusted request and connection sequence

1. Verify bearer signature, algorithm and required claims.
2. Resolve the immutable UUID and check current enabled user via narrow identity function.
3. Lookup only `(userId, requestedTenantId)` membership; that query also checks enabled state. Missing membership/inaccessible tenant has the same 403 response. No stale authorization cache exists.
4. Begin a bounded tenant transaction with Spring `JdbcTransactionManager` / `TransactionTemplate` on the runtime datasource.
5. `JdbcTemplate` obtains the transaction-bound connection; its connection callback calls the unchanged `PostgresTenantContext.apply(connection, authorizedTenantId)`.
6. On that exact connection, execute a prepared real `SELECT id FROM platform.tenants WHERE id = ?` under runtime forced RLS. An invisible/missing row fails closed; no echo-only endpoint.
7. Commit/rollback clears the local context before pool reuse. Only then return safe tenantId, userId and database role.

The application authorizes before starting tenant access. A membership change racing an already authorized in-flight request may complete that request; subsequent requests read current state and are denied. RLS constrains an asserted UUID, not its authenticity: compromised runtime credentials/arbitrary SQL can set another GUC, as documented in [ADR 0001](0001-postgresql-tenant-isolation.md). No claim is made that RLS protects against trusted application compromise. No session-level tenant setting, ThreadLocal, or independent JPA connection is used.

Runtime pool remains capped at four, migration at two, operator at one; existing connection/statement/lock timeouts remain. A successful context request performs one enabled lookup, one exact membership lookup, one set_config and one indexed registry SELECT; no N+1, full membership loads, password hashing on bearer requests, external calls, or authorization cache. Request logs record status, elapsed milliseconds and server-generated correlation ID without identifiers, URLs, query strings or credential data. No latency benchmark is asserted.

## Offline bootstrap and limitations

See [authentication operations](../../engineering/authentication-operations.md) for exact key and bootstrap commands. The explicit `identity-bootstrap` profile runs no HTTP server, JPA entity manager, or Flyway, uses only operator credentials, validates input and atomically inserts a tenant, user and OWNER membership. Stable operator-supplied UUIDs make repeat execution safe: the exact existing triple returns unchanged, including its password, enabled flag and membership; mismatches or partial existing records fail and roll back. No public bootstrap, seed user, normal-startup account creation, or broad administration CLI exists. Operators are privileged identity creators and must keep this credential separate from runtime.

Limitations include local-only throttling, no refresh/revocation list, no public registration/reset/email verification/MFA, no frontend or Python auth, no management endpoints, no overlapping key rotation, and no production secret/TLS product selection. Disabled users and removed memberships are enforced live. Token theft grants identity access until expiry or account disabling; client token storage is outside this task. External OIDC may later replace local credential issuance behind the identity/token boundary after issuer, subject mapping, trust and migration contracts are approved; it is not implemented.

## Verification

Testcontainers covers a fresh database and a V1→V2 upgrade, real runtime privilege denials, parameterized identity functions, login success/failures, strict input, JWT rejection cases, enabled-state/membership revocation, both-tenant selection, database-derived roles, hidden registry rows, same physical connection evidence, rollback and pool cleanup, and the real offline bootstrap profile. Signing pairs are generated solely for tests in temporary files with owner-only permissions and deleted afterward; no private key is committed or production key generated in CI. EAAP-002 isolation tests remain active. See [EAAP-003 delivery evidence](../../tasks/EAAP-003.md) for checks actually executed.
