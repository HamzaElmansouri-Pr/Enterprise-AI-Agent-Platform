# ADR 0005 — Controlled agent execution

Status: implements approved EAAP-006; pending independent review. Builds on accepted [ADRs 0001–0004](../README.md) and [AGENTS.md](../../../AGENTS.md). No later milestone is approved here.

## Trust and execution sequence

Spring's new `execution` module owns customer JWT/current enabled state, current tenant membership, DRAFT agent access, daily admission, authorized knowledge retrieval, run persistence and citation mapping. All OWNER/ADMIN/MEMBER roles may execute. Python owns typed graph state, structured prompt assembly, one hosted invocation, output validation and actual usage. It receives no JWT, tenant/user UUID, database credential, document discovery capability or business tool. Source IDs are local to one execution, not reusable access grants.

Sequence: authenticate → authorize membership → load DRAFT agent under RLS → nonblocking process slot → atomic quota admission → existing EAAP-005 retrieval → reauthorize/load DRAFT configuration → persist RUNNING → invoke Python → independently validate answer/source IDs → reauthorize and recheck agent/run ownership → conditionally persist terminal result → return persisted success. All SQL uses short tenant transactions and the unchanged `AuthorizedTenant`/`PostgresTenantContext` helper. No transaction/connection remains held during embeddings, Python, or hosted inference. Agent archival after admission does not cancel an in-flight call; terminal persistence rechecks same-tenant ownership without requiring DRAFT. Revoked membership blocks terminal persistence, leaving safe stale recovery after authorized access returns.

No retrieval implementation is duplicated. EAAP-005 enforces selected agent associations, READY documents, fixed embeddings and exact tenant vector search. At most six passages and 8,000 Unicode characters are selected in deterministic retrieval order, trimming on code-point boundaries with source identifiers preserved. Current EAAP-005 chunks are <=1,200 characters, so six passages fit. No knowledge yields HTTP 422 `INSUFFICIENT_KNOWLEDGE`, a FAILED run, and no paid invocation. Retrieval failures before RUNNING still consume admitted quota but create no run. Nearest-neighbor scores are not confidence or proof of relevance; there is no invented threshold. The model may abstain with no sources; that also becomes `INSUFFICIENT_KNOWLEDGE`, never grounded success.

## Actual LangGraph and prompt hierarchy

`ExecutionState` is explicitly typed. An acyclic `StateGraph` executes `prepare_context` → `invoke_model` → `validate_answer` → `finalize` → END, with recursion limit five. There are no tools, loops, checkpoints, retries, memory, or alternative graphs. Failure exits the graph and becomes a sanitized runtime error.

A platform system message enforces grounding and evidence handling. Stored agent instructions are a subordinate developer message. Authorized passages and the question are JSON data in a user message, explicitly untrusted. Evidence text never enters the system/developer messages. Messages have a 24,000-character aggregate content limit, internal request a 128 KiB byte cap, instructions <=10,000, question <=1,000, passages <=6 × 1,200. This is a deterministic input-size budget, not an exact tokenizer count; worst-case UTF-8 tokenization remains bounded by encoded input bytes. Output is <=800 provider tokens and <=6,000 answer characters. No second local generative model is loaded.

Prompt separation mitigates injection but cannot eliminate it or hallucination. Tenant instructions remain untrusted configuration. Authorization is enforced outside prompts. Neither valid references nor high similarity prove factual support; broader answer-quality/adversarial evaluation remains necessary before production.

## Hosted provider contract

Python's narrow async `Provider.complete` accepts bounded messages and returns `Completion` (typed answer/source IDs, fixed model ID, nullable actual token usage). Normal runtime constructs only `OpenAIProvider`; deterministic adapters exist only in tests. Startup, health, migrations, agent management, embeddings and retrieval require no provider key. Execution without a key/approved model/bounded settings returns 503 `MODEL_UNAVAILABLE`.

The pinned OpenAI Python SDK is **2.37.0** (lockfile includes transitive versions). The single allowed snapshot is **gpt-5.4-mini-2026-03-17**, explicitly configured by the operator, with `responses.parse(text_format=Answer)`, strict JSON Schema, `reasoning.effort=none`, `store=False`, no tools and `max_retries=0`. Supported structured output and model snapshot compatibility were verified against [OpenAI structured outputs documentation](https://developers.openai.com/api/docs/guides/structured-outputs) and the [model documentation](https://developers.openai.com/api/docs/models/gpt-5.4-mini); installed SDK parsing is exercised with a mock HTTP transport. **No real hosted call has been authorized or executed as task validation.** Account access/availability still require operator verification; no silent model substitution occurs.

The API URL is fixed to `https://api.openai.com/v1`. Environment/caller base URLs and proxy routing are not used. Settings: `OPENAI_API_KEY`, exact `EXECUTION_MODEL`, output token cap 1–800 (default 800), provider timeout 1–40 seconds (default 30). HTTP connections are bounded, redirects disabled, total provider call has an asyncio deadline, and SDK retries are disabled. Incomplete/refused/invalid output fails safely; there is no paid JSON repair. Usage is actual provider metadata, or null when absent. A timeout can still incur provider charges; no exactly-once claim or automatic replay is made. `store=False` is not a guarantee of zero provider-side retention; customer content leaves the local trust boundary and provider/account data controls require production review.

## Citation contract

Spring assigns S1–S6 only to the selected passages and keeps their actual document UUID, chunk UUID, filename and nullable page. Python receives source IDs and passage text only. The model returns answer/sourceIds; both runtimes reject invalid shape, excessive output and unknown references. Empty citations abstain; duplicates are deduplicated. Spring maps only its original source dictionary, never model-supplied document/page metadata. Persisted citations contain real metadata, never complete context. TXT pages remain null.

## Lifecycle, schema and recovery

Forward migration **V5__controlled_agent_execution.sql** adds `platform.agent_runs` and `platform.agent_run_daily_quota`; V1–V4 remain unchanged. Run identity, immutable creator/question, lifecycle constraints, same-tenant agent composite FK, user FK, bounded answer/citations/usage, completion timestamps and a partial stale-owner index enforce the contract. RUNNING → SUCCEEDED or FAILED only. Runtime gets SELECT/INSERT and only named terminal column UPDATE privileges, no DELETE/TRUNCATE/identity or question updates. RLS is ENABLE+FORCE on both tables. Update policy and SQL condition require RUNNING; terminal rows cannot be overwritten. RLS isolates tenant scope; application queries additionally bind agent, immutable user UUID and run UUID. OWNER/ADMIN cannot read another user's runs.

Results are returned as successful only after durable terminal persistence. DB errors after the provider response emit only correlation/run IDs; they never log the answer or provider exception. RUNNING rows older than 180 seconds become FAILED/`EXECUTION_INTERRUPTED` on the next authorized start/status request for the same agent and creator. No call is replayed. This lazy recovery deliberately avoids a new scheduler or privileged cross-tenant dispatcher; an untouched run remains RUNNING until such access. Late finalization is fenced by status and the same 180-second cutoff. Database unavailability or membership revocation may defer recovery.

Questions/answers are private customer content. Their persistence needs a future retention, deletion, backup, encryption and access-audit policy before production. No deletion API, context/raw payload storage or hidden chain-of-thought capture is added. Daily quota rows also need future retention housekeeping.

## Budget and service security

Twenty admitted attempts per tenant per UTC day, including failures, are atomically reserved by a short PostgreSQL UPSERT with row serialization, maximum constraint and UTC-date policies. Retries consume another attempt and cannot bypass quotas. Admission commits before retrieval; later failure never rolls it back. Unauthenticated, invalid, inaccessible-agent and process-busy requests are not admitted. Default two nonblocking Spring slots cover retrieval plus runtime, providing a conservative bound of two in-flight model invocations per process; no waiting request queue. Python also has two nonblocking execution slots. Embedding's existing single inference slot/worker is unchanged. Bounds are per process, not global across replicas. No billing or cost forecast is implemented.

Dedicated `POST /internal/executions` uses timing-safe `X-Execution-Secret` checking against a 32–128 visible ASCII random `EXECUTION_INTERNAL_SECRET`, distinct from embeddings. Unknown JSON keys, duplicate keys, malformed Unicode, arbitrary model/graph/URL fields and oversized bodies are rejected without echoing input. Python never imports graphs or fetches URLs from requests. Java uses the internal network, three-second connect and 50-second complete-response deadline, cancellation and 64 KiB response cap. Python's complete graph deadline is 45 seconds. Credentials and confidential text are redacted from DTO representations and logs. SDK/HTTP client diagnostics are disabled. Execution explicitly disables LangGraph's existing transitive tracing context/callbacks, including inherited tracing environment settings, so private graph state is not exported to a trace backend. Telemetry records run/correlation IDs, status, fixed model identity, duration, known usage and safe failure categories only.

`compose.execution.yaml` adds no service, supplies the shared execution secret only to Spring/Python and provider credentials only to Python, and removes Python's host port. Use after auth+knowledge overlays; no DB credentials are given to Python or frontend. The trusted Docker network/shared secret is a development boundary, not mutual TLS or workload identity. Production isolation, key rotation, egress control, TLS and coordinated limits require future decisions.

## Public API and deferred capabilities

`POST /api/v1/tenants/{tenantId}/agents/{agentId}/runs`: strict JSON `{message,topK?}`, topK default5/range1–6; 16 KiB body; no query parameters or client authority fields. HTTP200 is persisted SUCCEEDED with runId, agentId, answer, deduplicated citations, nullable usage, durationMs and modelId. Failure returns sanitized code and runId when created. `GET .../runs/{runId}` returns only the creator's persisted RUNNING/SUCCEEDED/FAILED outcome, requires current enabled membership and same-tenant agent ownership, and permits status reads after archival. Responses use no-store.

Errors: authentication401, membership403, inaccessible agent/run404, archived start409, invalid400, daily/process bound429 (`Retry-After:60` is a conservative retry hint; quota resets at UTC midnight), no knowledge422, unavailable configuration/runtime503, provider/runtime output502, provider deadline504, unexpected persistence/runtime500. Exact Bearer routes receive scoped CSRF exemptions; all other default-deny and CSRF rules remain.

Streaming, chat UI/history, multi-agent planning, tools/business actions, approvals, CRM/email, scheduling, retries/replay, provider marketplace, analytics, billing and production hosting are deferred to approved future milestones.
