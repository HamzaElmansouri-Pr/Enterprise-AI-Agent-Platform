# ADR 0006 — Trusted Tool Gateway and human approval

Status: implements approved EAAP-007; pending independent review. EAAP-000–006 are accepted. Extends [ADR 0005](0005-controlled-agent-execution.md) and the [existing identity/RLS boundary](0002-authentication-and-tenant-authorization.md). [Operations](../../engineering/tool-approval-operations.md) gives exact offline procedures.

## Ownership and one allowlisted operation

Spring's `tool` module is the trusted gateway. Domain records validate the fixed payload, immutable proposal digest and lifecycle preconditions. Application use cases check current enabled membership/permissions, orchestrate short tenant transactions and dispatch through an explicit registry. Infrastructure implements prepared JDBC storage, the one concrete PostgreSQL follow-up-task handler and bounded internal generation HTTP. API transport validates strict JSON and maps safe responses. The accepted tenant capability/context/transactions and V1–V5 are unchanged.

`ToolRegistry` has exactly one definition: `admissions.create_followup_task`, version1, argument fields title/description/priority, permission TENANT_MANAGE, approvalRequired=true and an explicit Java handler reference. No reflection, dynamic loading, caller-selected classes, runtime registration or tool discovery exists. `JdbcProposalStore.createFollowup` is the concrete handler: one real tenant-owned PostgreSQL OPEN task, with sourceProposalId and current executor as createdBy. It executes only inside the gateway transaction. A later approved tool can add an explicit definition/handler/schema migration while reusing approval/audit orchestration; this is not a plugin framework.

Arguments: nonblank valid Unicode title<=120 code points with no C0/C1, bidi override/isolate or line/paragraph controls; nonblank description<=1,000; priority LOW/NORMAL/HIGH. NUL/malformed Unicode and URL schemes/destinations are rejected; extra fields for tenant/user/role/credentials/SQL/commands are forbidden. Title/description are data inserted through parameters, never evaluated as code, SQL, shell or file operations. A rationale is required, nonblank and <=500 code points. Text is preserved exactly rather than trimmed/normalized after review.

## Authority and separation of duties

Every operation uses the immutable authenticated UUID and live database membership, including enabled state. Caller JWT role/tenant claims, headers, model output and body authority fields confer no permissions. OWNER/ADMIN may manually submit, view all proposals, approve/reject and execute. MEMBER may generate and view only their own proposals; all three roles may view tenant follow-up tasks. Cross-tenant/inaccessible proposals are404, missing membership403, invalid/disabled/expired authentication401. Proposal creation requires same-tenant DRAFT agent ownership; existing immutable proposals can still be reviewed/executed after archival, since this milestone specifies no cancellation-on-archive contract.

Approval is a separate explicit POST by an OWNER/ADMIN whose user UUID differs from the creator. A single-user tenant cannot approve its own proposals. No public account/role management or automatic second-user provisioning is added. Rejection may be performed by the creator if they are a manager; only self-approval is prohibited. The approver's identity/decision is historical evidence; every later executor must independently have current manager membership. Revoking an actor blocks subsequent requests, without rewriting previously recorded decisions.

The caller must provide expectedPayloadDigest for approval and rejection. Spring checks the stored digest against a recomputation and the expected value. Canonical encoding is SHA-256 over UTF-8 `EAAP-007/v1\n`, then this fixed sequence of fields, each encoded as decimal UTF-8 byte length, colon, exact UTF-8 bytes: proposal UUID, tenant UUID, agent UUID, creator UUID, tool name, decimal tool version, title, description, priority, rationale. Canonical UUID spelling and enum names are server-generated; there is no Unicode normalization. Length prefixes remove concatenation ambiguity, and identities prevent approval-digest replay across otherwise equal proposals. This is an ordinary unkeyed digest, not a signature or protection against a fully compromised DB operator/runtime.

Approvals bind proposal/tenant/creator, approver, exact digest, decision, reason and timestamp/correlation ID. Immutable proposal arguments/ownership/version/digest cannot be updated by runtime grants or ordinary UPDATE triggers. Decision/task rows have no runtime UPDATE/DELETE privilege. Composite FKs bind the decision to the proposal's tenant/digest/creator and the task/result to the same proposal. A CHECK forbids approval by the creator; a trigger additionally checks live manager membership and PENDING state when recording a decision.

## State machine, transaction and replay

PENDING_APPROVAL → APPROVED or REJECTED; APPROVED → EXECUTING; EXECUTING → SUCCEEDED or FAILED. REJECTED/SUCCEEDED/FAILED are terminal. No reapproval, argument editing, automatic retry or resurrection exists.

Creation commits PENDING only. Approval commits only its decision/state; no task mutation occurs. Execute obtains a row lock, verifies the immutable digest/approval/other approver/tool name/version/schema/current manager, and conditionally claims APPROVED. The handler uses the exact approved arguments. Task insertion and terminal transition commit in one short transaction under unchanged tenant RLS. Unique (tenant_id,source_proposal_id) prevents duplicate effects, and the proposal's task FK points to the same proposal's task. A task-insert validation trigger independently checks EXECUTING, approved digest, executor identity and exact argument equality. No in-memory lock is the effect/idempotency authority.

The internal handler runs inside a JDBC savepoint. A handler exception rolls back its mutation, then persists FAILED/TOOL_EXECUTION_FAILED and executor/correlation/timestamps in the outer transaction, returning a terminal FAILED representation with HTTP200. FAILED is not retryable. If the database cannot persist the terminal state, the outer transaction rolls back claim and task together, returns sanitized500 and leaves APPROVED for an explicit later attempt. A connection/process crash likewise rolls back the entire uncommitted transaction. A deferred commit constraint forbids committing a stranded EXECUTING state, so no new recovery scheduler is needed for this SQL-only tool.

Concurrent approvals/rejections serialize on the row; one wins, others409. Concurrent executions serialize and either perform the effect or return the existing immutable SUCCEEDED result. Repeated SUCCEEDED execution is HTTP200 with the same taskId/original executor, never an additional task or changed audit identity. Other invalid/terminal execution states409. PostgreSQL UPDATE RLS hides terminal rows from FOR UPDATE; the adapter falls back to a read only for immutable terminal rows, preserving restrictive UPDATE policies. SQL lock contention is bounded and maps to409 proposal_busy where recognized. There is no unlimited queue or unbounded transaction.

A lost commit acknowledgment can leave an already committed terminal outcome even though the client sees500. Inspect GET before an explicit repeat; immutable success replay and source-proposal uniqueness remain authoritative. Separate newly submitted proposal UUIDs are separate actions, not semantic deduplication of equal titles.

These guarantees cover one local PostgreSQL effect. Future external HTTP/CRM tools require separately approved idempotency keys, durable dispatch/recovery, ambiguous-response reconciliation and possibly compensation. A DB transaction alone cannot provide exactly-once external delivery.

## V6 persistence, audit and privacy

`V6__tool_gateway_and_approvals.sql` adds only tool_proposals, tool_approval_decisions and admissions_followup_tasks. All have UUID primary keys and ENABLE+FORCE tenant RLS. Runtime gets SELECT/INSERT plus named proposal lifecycle/executor/result column updates only. No BYPASSRLS/ownership/DDL/DELETE is granted. Fixed-search-path SECURITY INVOKER validation/transition/commit triggers add no privileged dispatch or tenant discovery capability. RLS scopes an asserted tenant; trusted application membership and MEMBER creator filtering remain mandatory under the established runtime-credential-compromise limitation.

Proposal rows persist creator, selected agent/tool/version, exact bounded arguments/rationale/digest, creation correlation/time and execution actor/correlation/time/status/failure/result task. The one immutable decision row records reviewer, digest, decision/reason/time/correlation. This is sufficient durable audit evidence for this milestone; no fourth event store is needed. Normal logs contain only IDs, safe state/failure category, timing and actual known model usage, never arguments, rationale, private intent/instructions, JWTs or secrets. DTO/domain string representations redact customer content. Missing/invalid private JSON is sanitized before framework exception logging.

Ordering is creation timestamp DESC then UUID DESC; lists use one size+1 query, size1–100/default20, page offset<=10,000. Proposal decisions are left-joined in the same query (no N+1). Separate tenant/creator indexes support manager/member listing; task source uniqueness supports replay integrity. The existing four-connection pool, five-second tenant transaction and three-second query/lock limits remain. Manual submissions do not consume a paid-model budget, but storage retention/authorized-write abuse limits need production review. Arguments, rationale and reviewer reasons are customer content: future retention/deletion, encryption, backups and access-audit requirements apply.

## Narrow AI proposal path

A separate actual typed StateGraph executes prepare_context → invoke_model → validate_proposal → finalize, once, with recursion limit5. It receives only server-loaded agent instructions and validated intent<=1,000 characters plus request/correlation UUIDs. It does not fetch knowledge or change EAAP-006's grounded Q&A. The intent is JSON user data subordinate to platform instructions; tenant configuration cannot override authorization. Output is only fixed toolName, strict arguments and short rationale. There is no tool node/function invocation, model-approved status, customer JWT, database access, model-selected tenant/role, arbitrary URL/import or execution capability. Python cannot approve or execute anything.

The existing OpenAI adapter now exposes a second fixed-schema method through its same private request implementation: pinned SDK/model/URL, structured output, no tools, reasoning none, <=800 output tokens, no retries, store=false and existing timeout controls. There is no new provider/framework/key or production fake mode. Supported schema parsing follows [OpenAI's structured-output contract](https://developers.openai.com/api/docs/guides/structured-outputs). No paid call was authorized or made for validation; mocks demonstrate contracts, not real model proposal quality or resistance to prompt injection.

Spring Q&A and proposal generation share one ExecutionAdmission bean with two nonblocking process slots and the same atomic agent_run_daily_quota allowance of20 attempts/tenant/UTC day. Admitted failures count; no transaction is held during inference. Python uses the same two execution slots for both graphs, the same tracing suppression and45-second graph deadline. Assembled prompt content is bounded to24,000 characters, internal body128KiB, Java complete-response50seconds/64KiB. `/internal/tool-proposals` reuses the dedicated X-Execution-Secret/internal network boundary and strict duplicate/Unicode/unknown-field validation. Provider misconfiguration503 leaves manual proposals, health, existing management and knowledge usable. These process limits are not global across replicas.

A generated proposal is independently revalidated by Spring before PENDING persistence; unsupported output never becomes an authorized action. JSON validity and prompt text are not authorization. Injection fixtures instructing approval bypass, arbitrary tools, tenant/role forgery, cross-tenant effects, token reuse and mutable payloads must remain powerless against the gateway's external checks. Valid schema does not prove business intent correctness, and prompt separation does not eliminate injection/hallucinations. Humans must review exact arguments.

## API and operations

Under `/api/v1/tenants/{tenantId}`:

| Route | Contract |
| --- | --- |
| POST `/agents/{agentId}/tool-proposals/generate` | Strict `{intent}`, all roles, persisted PENDING,201; shared paid budget |
| POST `/agents/{agentId}/tool-proposals` | Strict `{toolName,arguments,rationale}`, OWNER/ADMIN, PENDING,201; no model call |
| GET `/tool-proposals` | Bounded manager/all or MEMBER/own page |
| GET `/tool-proposals/{id}` | Exact immutable payload, digest, creator, decision and execution metadata |
| POST `/tool-proposals/{id}/approve` | Strict `{expectedPayloadDigest}`, other manager only; no task effect |
| POST `/tool-proposals/{id}/reject` | Strict `{expectedPayloadDigest,reason}`, manager; no task effect |
| POST `/tool-proposals/{id}/execute` | Manager, no body; approved validated dispatch or immutable success replay |
| GET `/admissions/followup-tasks` | Bounded tenant-isolated read for all roles |

Public JSON bodies are capped at16KiB. Unknown/duplicate/trailing fields, wrong types, forged authority, unexpected query parameters and generic execution bodies fail400. Wrong media415; missing membership403; unknown/inaccessible404; transition/digest/busy409; provider quota/process bound429; provider503/502/504 and unexpected500 remain sanitized. No-store applies to responses. Exact stateless Bearer write paths receive CSRF exemptions; all other deny/CSRF rules remain.

Apply V6 only through reviewed offline migration credentials. Fresh and V5→V6/repeat paths are tested. FK/index/trigger DDL can acquire metadata locks; back up/review existing volumes. Failure rolls back DDL; applied defects need a new forward migration. No development data is automatically migrated, second user created, privilege elevated, history rewritten or branch merged by this task. CRM/email/SMS/WhatsApp, browsing/shell/SQL tools, tool chaining, dynamic plugins, approval UI, scheduling, memory, distributed brokers, billing and production deployment remain excluded.
