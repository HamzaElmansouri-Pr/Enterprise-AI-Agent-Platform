# ADR 0009 — Secure agent conversations

Status: implements the approved EAAP-010 specification; pending independent review. Baseline includes merged EAAP-009 PR12 at `c99521e5e9500032f84dbac629475338304d966c`. See [operations](../../engineering/conversation-operations.md) and [delivery evidence](../../tasks/EAAP-010.md). This record describes the implementation, not architect acceptance.

## Ownership and persistence

Spring owns authentication, enabled-user/current-membership checks, tenant/agent/creator authorization, persistence, reservation, quota, retrieval and validated citation mapping. All roles can use their own conversations. OWNER/ADMIN have no supervisor access. Missing membership returns403; an authorized tenant/agent scope with an absent or another creator's conversation returns404. Request bodies cannot choose user, tenant, agent or authority. Agent/conversation ownership cannot change. Membership removal blocks subsequent access without deleting history. Already-authorized in-flight operations retain the existing authorization race limitation.

V8 is forward-only; V1–V7 are unchanged. It adds:

- `conversations`: UUID, tenant, agent, immutable creator, title≤120Unicode characters, OPEN/CLOSED, creation/update timestamps. The listing index covers tenant/creator/agent/creation ordering. There are at most20 conversations per user/tenant across all agents, including closed records. An invoker trigger serializes quota checks with a transaction advisory lock.
- `conversation_turns`: immutable tenant/agent/creator/conversation, client request UUID, ordinal1–100, one unique run UUID, stable USER and ASSISTANT message UUIDs and creation timestamp. Unique keys enforce request ID and turn ordering per conversation. Composite foreign keys bind both conversation and source run to the same tenant, agent and creator. V8 adds the corresponding unique run identity constraint.

Each durable logical turn projects exactly two messages. USER ordinal is `2*turnOrdinal-1`, ASSISTANT ordinal is `2*turnOrdinal`. Content, answer state, citations, model identity, actual usage and failure metadata remain in the existing `agent_runs` row. USER is SUCCEEDED once reserved; ASSISTANT mirrors RUNNING/SUCCEEDED/FAILED, with null content unless an answer succeeded. This two-table design avoids a second incompatible execution lifecycle, duplicate question/answer storage, copied retrieved evidence or full provider payloads. Message pages include stable IDs, requestId, sourceRunId, ordinal, role, content, status, citations and timestamp. Failed user turns count toward the100-turn limit.

Both tables ENABLE/FORCE RLS for tenant **and creator** using transaction-local `app.tenant_id` and `app.user_id`. Trusted application code sets user context inside the existing authorized tenant transaction. Commit/rollback clears both values. Runtime receives SELECT/INSERT and only conversation title/status/update-time UPDATE. It cannot update turn records, change creator/agent/identity, delete history, truncate, own tables or bypass RLS. The conversation UPDATE policy exposes only previously OPEN rows, preventing reopening. Trigger functions are fixed empty-search-path SECURITY INVOKER with revoked PUBLIC execution, not new elevated identity capabilities; PostgreSQL invokes the installed triggers during allowed writes.

These context settings assert trusted application identity; they are not cryptographic PostgreSQL authentication. Compromised application code/runtime SQL credentials can assert another known actor. Existing global identity/run capabilities retain their documented trust boundaries. Protection against privileged schema owners, administrators or complete runtime compromise is not claimed.

## State, ordering, idempotency and admission

Creation needs a DRAFT agent and performs no provider call. Rename requires OPEN; close is terminal, refuses an active turn, and repeated close returns409. Archived agents reject creation/new messages while existing messages and metadata remain readable. Metadata rename/close remain permitted on an archived agent's OPEN conversation. The update timestamp advances on reservation or explicit metadata change; it is not a separate provider-completion timestamp.

Sending strictly accepts `{message,requestId}`. The current question is valid nonblank Unicode,≤1000code points. The request ID is scoped to the conversation. Same ID/same question returns the stored turn; same ID/different question returns409. Completed replay remains readable after closure/archival. A missing reservation's outcome returns404. Neither replay nor status reads intentionally dispatch a model call or charge a second admission.

A fresh turn takes the existing process-wide two-slot `ExecutionAdmission` and a short database transaction. It locks the conversation, rechecks ownership/state and request ID, checks active runs/100 turns, consumes one existing tenant daily quota admission, creates a RUNNING run and inserts the turn atomically. Another new request while the conversation has an active RUNNING turn receives409. Database trigger checks independently enforce sequential ordinals, OPEN/DRAFT,100 turns and one active run for ordinary runtime inserts. A duplicate reservation loses the race without another quota admission. Reservation failure rolls back quota/run/message position together.

The quota is the existing20 admitted attempts per tenant/UTC day shared with single-turn execution and proposal generation. Retrieval/model failures still consume that logical attempt. Process-slot429 before reservation consumes none. A replay already found in persistence is readable without acquiring another process slot. A slot race before reservation can still return busy; the outcome GET remains authoritative. No second unlimited conversation budget, queue or broker exists.

After commit, authorized EAAP-005 retrieval uses the current question and the selected agent's current READY associations. No database transaction remains open over embedding or hosted inference. Current membership and DRAFT configuration are checked again after retrieval. Completion is fenced through the existing conditional RUNNING run update and180-second deadline. Answer/source validation and evidence preparation are shared with EAAP-006 through `GroundedAnswer`, preserving its existing behavior.

## Failure, restart and retry semantics

A reserved turn returns HTTP200 with durable `status` and `result`; FAILED is an execution outcome, not an invented successful answer. Provider/model errors retain safe failure codes and actual validated usage where available. Unknown usage stays null. Validation/authorization/lifecycle/admission errors before reservation retain400/401/403/404/409/429. Unexpected database errors return sanitized500 and never claim a durable success.

A crash after reservation, ambiguous timeout or failure to persist may leave RUNNING. Authorized message/outcome reads or the next send recover runs older than180seconds to FAILED/EXECUTION_INTERRUPTED. No worker automatically retries inference. Late responses cannot overwrite terminal outcomes or an expired lease. The source run and request ID survive actual process restarts. Successful replay returns the same durable run/result; a pending or recovered request does not run again. If membership is revoked during inference, completion reauthorization may fail; history is retained and recovery waits for later authorized access.

This is durable application idempotency and at most one intentional dispatch per reserved turn, **not exactly-once external execution or billing**. A provider might have processed a request whose response was lost, or the process could crash before sending. The system deliberately does not guess and retry that reservation. Operators must inspect outcomes; a new logical turn requires a new explicit user action and UUID.

## Context selection and LangGraph

Only SUCCEEDED prior turns enter history. Select the most recent six complete pairs, newest first for selection, stopping before8000total Unicode characters and then reversing to chronological order. Pairs are never partially included. Pending, failed, incomplete and other conversations' turns are excluded. The current RUNNING turn is not its own history.

Existing Spring-authorized evidence supplies at most six passages and8000characters. Stored instructions remain≤10000 and the current question≤1000. The dedicated internal route is POST `/internal/executions/conversation`, using the same execution secret, Python service, two slots, deadlines, fixed approved provider/model, output-token ceiling800, no SDK retry and disabled trace export. The accepted single-turn route still forbids history. No tenant/user/customer JWT, database credential, arbitrary URL or tool is sent to Python.

The typed `ConversationRequest` adds only bounded complete history pairs to the existing execution schema. The real existing acyclic LangGraph graph handles both contracts, with one provider node and no conversation cache. Platform instructions, subordinate stored configuration, and JSON-delimited untrusted evidence/current question/history remain separate. Prior assistant text is not promoted to a system instruction. Python independently validates history/passages and rejects assembled content over40000characters before provider invocation; single-turn keeps its24000 bound. Escaped JSON and delimiting text count toward these aggregate limits. Requests are byte-capped256KiB (single-turn remains128KiB).

Only current evidence's S1–S6 identifiers can be returned. Spring maps them to exact document/chunk/filename/page metadata; historical citations persist independently of later association removal and do not confer access to source bytes. No second retrieval pipeline, query-rewriting model, summarization, vectorized memory, training, autonomous loop, tools or business approval is added. Delimiters reduce instruction ambiguity but cannot eliminate prompt injection or guarantee answer quality.

## React and privacy

Conversations is an added console area over the existing same-origin client. It lists current-user conversations by agent, supports OPEN and archived-agent history, title editing, terminal close confirmation, chronological20-message pages and safe ordinary text bubbles/citations. Earlier/later pages are explicit; no unbounded history or polling exists. The existing cost acknowledgment applies to conversation sends and resets with the existing session lifecycle.

A fresh logical send generates `crypto.randomUUID()` before the request. A synchronous guard prevents duplicate sends. Pending IDs live in a console-scoped memory registry, retained across feature navigation/unmount within that session. An ambiguous response disables another send and offers explicit read-only outcome GET. A definite rejected send releases its draft, but transport/5xx ambiguity retains the ID even if a subsequent outcome GET returns404; there is no automatic POST replay. Persisted messages also expose request IDs so outcomes remain inspectable after reauthentication. Logout/tenant switch destroys private UI/session state; login again reads persisted history from Spring. Tokens/passwords are not written to browser storage, cookies, URLs or logs. Pending request IDs stay in console memory and creator-authorized API paths, without navigation-URL/storage persistence. Operational identifiers can appear in protected server diagnostics.

PostgreSQL stores customer questions and successful assistant answers, citation snapshots, usage/failure/run metadata and ownership identifiers. Only the current enabled creator with current membership can read through these APIs. Configured hosted inference receives selected history, instructions, question and authorized evidence; provider request storage is disabled using the existing adapter, but that flag is not a guarantee about every provider retention practice. Backups contain conversation content and need operator protection. Revocation and archival preserve history. No physical deletion/retention workflow, customer compliance guarantee, long-term learning or cross-conversation export is claimed. Production retention/deletion/compliance and future long-term memory require separately approved designs.

## Resource and rollout implications

Lists have size1–100, offset≤10000, size+1 hasNext queries and deterministic ordering. Message order is ordinal rather than timestamp. History selects at most six successful rows from the bounded100-turn conversation; there is no N+1 query per message and no application/Python cache. Run identity uniqueness adds one index and can require a table scan/lock at migration. Parent/foreign-key/index/trigger DDL and quota serialization should be reviewed against production volume; back up and use the offline migration profile in a maintenance window. Four-service memory/CPU limits and pool/query/lock deadlines remain unchanged. No measured latency claim is made.

Tests and isolated acceptance evidence are recorded in [EAAP-010](../../tasks/EAAP-010.md). No paid hosted-quality test is part of default validation. PR remains unmerged pending independent review.
