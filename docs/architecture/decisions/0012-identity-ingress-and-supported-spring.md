# ADR 0012 — Login ingress and supported Spring baseline

Status: implements the explicitly approved EAAP-013 modernization; pending independent architectural/security review. EAAP-000–012 are accepted. Accepted master is `68d51a76e904e1c86e2f8c4ebd6512be720eccef`. This task explicitly authorizes Boot 4 despite the initial Boot 3 baseline in AGENTS.md. No production launch is authorized.

## Boundary and abuse controls

The old five-attempt peer quota in Spring counted the Nginx container, combining every pilot user into one bucket. Forwarding headers were correctly ignored; enabling their interpretation would create an unnecessary identity channel.

Keep client-origin enforcement at Nginx. It must receive clients' TCP connections directly. A native 1 MiB shared-memory zone keys only normalized `POST /api/v1/auth/login` requests by `$binary_remote_addr`; every other method/path has an empty key. The configured leaky bucket is 10 requests/minute with burst 9 and `nodelay` (ten immediate requests from an empty bucket). Excess requests receive generic JSON 429, `X-Login-Limit: ingress`, and `Retry-After: 6`, the nominal single-slot refill interval. This hint assumes the peer stops sending; competing traffic can consume that slot. No request queue, request body/access log, static-resource throttling or external product is added. Limiter diagnostics are below the error-log threshold because they include request URIs. Zone capacity is bounded; native eviction/allocation failure semantics apply. See [Nginx's module contract](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html).

Spring independently retains 20 JSON login admissions/process/UTC minute and two nonblocking expensive-verification slots. All admitted attempts count, including successes, invalid bodies, unknown users, password mismatches, and requests rejected by a busy hash guard. Query parameters are rejected before admission; unsupported media types are rejected by routing. These cannot reach password verification. Successful login never clears the process budget. A fixed minute can admit 40 requests across its boundary; the hash cap still applies. No process-spanning guarantee is claimed.

An active normalized identity can occupy at most one of the two slots. The key is full HMAC-SHA256 of the existing `Email` value (strip plus Locale.ROOT lowercase), with a fresh 256-bit process key. At most two digests exist; no raw emails/passwords, per-account failure history, persisted keys or account-labelled metrics exist. A permit removes its digest on every return/exception and closes idempotently. Lifetime is only the bounded verification operation (database deadlines and fixed Argon2 work), rather than a cooldown or a TTL cache. Process termination discards everything. No timer can expire a permit while its hash still runs and accidentally exceed concurrency.

We deliberately choose active-identity admission rather than a failure-count account cooldown: an attacker cannot renew a post-attempt account lockout. Concurrent verification of the same account returns generic 429, whether or not that account exists. Full-digest collision probability is negligible; a collision would temporarily serialize unrelated work. HMAC protects against straightforward offline email enumeration of a captured tracker alone; process-memory compromise can expose its key and other application secrets. Simultaneous guesses can still race a legitimate owner, and distributed attackers can exhaust the global budget. This is bounded workload protection, not comprehensive credential-stuffing or DDoS prevention.

Invitation acceptance keeps its independent accepted five-peer/twenty-process/two-slot policy, copied into its own guard so login changes cannot silently expand anonymous account creation. Its shared-proxy availability limitation remains documented for a separately reviewed invitation-control change.

## Origin trust and deployment assumptions

Nginx strips Forwarded, X-Forwarded-For, X-Real-IP, X-Forwarded-Host and X-Forwarded-Proto. Spring's `server.request.header.forwarded.strategy` is `none` in the pilot and validated at startup. No real-IP module trust rule, global framework forwarding support, custom proxy identity header or client role/tenant authority is introduced. Custom headers convey no authority. Python still disables proxy headers.

A NAT/shared-IP group shares the intentional ingress peer bucket; distinct actual TCP peers have distinct ingress buckets. Spring's global cap is intentionally shared, rather than an accidental five-login proxy bucket. A CDN/load balancer would become the observed peer and must not be inserted until an explicitly allowlisted upstream trust design is reviewed. Headers alone cannot distinguish clients behind it.

All four service boundaries, private networks, file secrets, readonly/nonroot containers, resource caps, private diagnostics and immutable image/revision checks remain. Privileged host/Docker operators are trusted. No database migration or development-volume operation is needed.

## Framework decision and compatibility

Select **Spring Boot 4.2.0**, stable GA released 19 November 2026. Official [release announcement](https://spring.io/blog/2026/11/19/spring-boot-4-2-0-available-now/), [current release metadata](https://api.spring.io/projects/spring-boot/releases/4.2.0), and [generation metadata](https://api.spring.io/projects/spring-boot/generations/4.2.x) were checked on 22 November. The latter identifies free OSS support through **31 December 2027**. Its nominal month-end initialReleaseDate is 30 November; the actual GA announcement and resolved Maven artifacts establish availability on the 19th. No commercial entitlement is assumed. [Framework 7.1 metadata](https://api.spring.io/projects/spring-framework/generations/7.1.x) has the same OSS end date. Recheck monthly and upgrade within that window.

Java 21 and pinned Temurin 21 images remain. [Boot requirements](https://docs.spring.io/spring-boot/system-requirements.html) support Java 17–27 and Servlet 6.1/Tomcat 11. Review sources: [Boot 4 migration](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide), [4.2 removals](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.2-Release-Notes), [Security 7 migration](https://docs.spring.io/spring-security/reference/migration/index.html).

The exact resolved compatibility matrix and advisory disposition are in [EAAP-013](../../tasks/EAAP-013.md). Boot manages the selected framework dependencies. Old Jackson/JDBC/Log4j overrides are removed after resolved-version review; a focused Tomcat11.0.29 override replaces managed11.0.27 for newly published Apache fixes. PDFBox and Bouncy Castle remain explicitly pinned.

Changes are integration-focused: modular webmvc/resource-server/Flyway and test starters; moved Boot health/security/environment/test packages and spring.factories registration; renamed offline JPA exclusion; Jackson 3 packages, immutable strict JsonMapper, property iteration and unchecked parsing exceptions; Testcontainers 2 artifact/package/non-generic container API. Strict duplicate/unknown/trailing JSON rejection is retained. Base-profile probes remain disabled to preserve the status-only development health response; private pilot probes remain enabled. No security auto-configuration, validation, business test, authorization or RLS is suppressed.

RS256/issuer/audience/expiry, Argon2id, live enabled identities and memberships, exact default-deny routes, scoped CSRF exemptions, invitations, creator isolation, tool approval/replay and V1–V8 contracts remain authoritative. Flyway owns schema changes; Hibernate DDL remains disabled. No schema/entity rewrite or V9 is introduced. The full HTTP/persistence/recovery/evaluation evidence is required before delivery acceptance.
